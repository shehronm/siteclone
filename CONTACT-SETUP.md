## Размещение

Vercel Framework Preset **Other**, корень этой папки, Node.js **24.x**, без команды frontend-сборки. Это готовый статический экспорт с Node.js API, а не исходный Next.js-проект для `next build`. `index.html`, `ru/`, `next-assets/`, `assets/` и `api/` должны попасть в один deployment. Хостинг только статических файлов не исполняет `/api/contact`.

При переносе в другой проект или замене тестовых настроек:

1. Создайте/настройте бота через @BotFather и сохраните токен в менеджере секретов.
2. Отправьте боту `/start`; для группы добавьте бота и напишите сообщение. Определите ID нужного чата через Bot API у себя, не публикуя ответ с приватными данными.
3. В Vercel → Settings → Environment Variables задайте `TELEGRAM_BOT_TOKEN` и `TELEGRAM_CHAT_ID` для Production и, при необходимости, Preview. Выполните новый deployment: изменение переменных не меняет уже созданную версию.
4. На опубликованном сайте отправьте одну контрольную заявку через «Start a project» / «Обсудить проект». Проверьте HTTP 2xx + JSON `ok:true`, success state и получение сообщения именно в нужном чате. После смены токена, чата или проекта прежнее подтверждение доставки не заменяет этот smoke-тест.
5. При переносе в другой Vercel-проект настройте его Firewall и мониторы отдельно: правило и настройки внешних сервисов не переносятся вместе с ZIP. В том же проекте проверьте охват нового домена.

Не помещайте токен в браузерный JavaScript, HTML, Git или отчёты. Для локальной работы используйте `vercel dev` с собственными переменными окружения. Обычный статический HTTP-сервер не запускает обработчик. `.env.example` содержит только шаблон; `.env.local`, cookies и данные Vercel-авторизации не должны входить в архив.

## Контракт формы и API

Форма проверяет обязательные поля, длины и email; сервер дополнительно проверяет типы, допустимую тему и пробельные значения. Успех требует HTTP 2xx и JSON `ok:true` нашего API после подтверждения Telegram. Ошибки сети/провайдера, таймаут, HTML вместо JSON и отсутствие настроек дают error state с сохранением данных. Без настроек API возвращает 503.

После успеха повторная отправка того же брифа блокируется до редактирования. Это UI-защита, а не гарантия уникальности между устройствами/перезагрузками. Если Telegram принял заявку, но ответ браузеру потерян, повтор может создать дубликат; для строгой дедупликации нужен общий внешний стор.

JSON ограничен 16 KiB: проверяются `Content-Length` и размер разобранного объекта, превышение →413. Неподдерживаемый метод →405, неверный content-type →415, повреждённый JSON/невалидные поля →400. Honeypot и ограничения полей дополняют действующий WAF. Общий IP делит квоту; fixed-window ограничение не заменяет защиту от распределённого злоупотребления.

Последний завершённый прогон серверных тестов Node.js — 14/14, Telegram в тестах подменён. Отдельно проверены mocked success/error/timeout, ложный HTTP 200, сохранение данных и UI ошибки 429 на EN/RU. 429 показывает общее сообщение об ошибке и позволяет повторить позже; API WAF не возвращал Retry-After в контрольном тесте.

## Наблюдение и действия при сбое

`api/health.js`: GET/HEAD →200 при наличии обоих значений настроек, иначе →503; POST →405. Ответ no-store и не содержит настроек. Эндпоинт не вызывает Telegram и не проверяет валидность токена у провайдера.

UptimeRobot настроен для главной страницы и `/api/health`. Владелец подтвердил активацию, предоставил скриншот health URL со статусом Up и интервалом 5 минут, подтвердил письмо Test Notification. Реальный down/up-инцидент не проводился. Проверка главной/health не обнаружит все отказы Telegram; нужны просмотр ошибок доставки и периодический контроль критического пути.

В Runtime Logs выводится только событие `contact.delivery` с исходом `sent`, `unconfigured`, `provider_rejected` или `provider_unavailable`; данные заявки, chat ID и токен не журналируются. При сбое проверьте событие, HTTP-ответ и наличие настроек. Оповещения по ошибкам функций отдельно не настроены: чтение логов и uptime-письмо не заменяют такой канал.

`monitoring.js` подключает Vercel Speed Insights на восьми HTML-страницах, исключает localhost, удаляет query/hash. На EN/RU скрипт и отправка метрик подтверждены HTTP 200 в синтетическом QA-браузере; полевые показатели пользователей ещё не оценены.

После перехода на `miro.website` обновите адреса мониторов и проверьте API через окончательный домен. Домен пока не перепривязывался. Регламент выпуска и границы аудита описаны в `PRE-DEPLOY-AUDIT.md`, изменения — в `QA-REPORT.md`.
